```text
Add a complete "Fix → Review → Verify → Complete" workflow to the existing Merchant Voice SaaS application.

IMPORTANT:
Do not redesign or rebuild the entire application. Extend the existing product and preserve the current UX, architecture, database, and functionality unless changes are required for this workflow.

CORE PRINCIPLE:

An internal team marking an issue as fixed must NOT automatically make the issue "Completed".

The correct lifecycle is:

Detected
→ Assigned
→ Acknowledged
→ Investigating
→ Fix Submitted
→ Ready for Review
→ Reviewed
→ Completed

A reviewer must verify the fix before the issue can become Completed.

==================================================
1. INTERNAL TEAM: SUBMIT FIX
==================================================

When the assigned internal team finishes their work, replace the simple "Resolve" action with:

[Submit Fix for Review]

Fix summary
Required

"What was changed?"

Resolution details
Optional

"What did the team do to address the issue?"

Evidence
Optional

Allow:
- text
- deployment/reference ID
- relevant notes
- attachment/link if supported by the existing architecture

Primary button:

[Submit for Review]

After submission:

Status becomes:

READY FOR REVIEW

Do NOT mark it Completed automatically.

==================================================

==================================================
12. UX PRINCIPLE
==================================================

Use this distinction everywhere:

"Ready for review"
=
The team says the work is finished.

"Completed"
=
An authorized reviewer has verified and accepted the fix.

Never use "Finished" as the final state.

Use:

READY FOR REVIEW

and:

COMPLETED

==================================================
13. QUALITY REQUIREMENTS
==================================================

The workflow must work end-to-end.

Test:

1. Issue is created.
2. Issue is assigned.
3. Team acknowledges.
4. Team investigates.
5. Team submits a fix.
6. Status changes to Ready for Review.
7. Reviewer receives notification/in-app alert.
8. Reviewer opens review screen.
9. Reviewer verifies evidence.
10. Reviewer accepts.
11. Issue becomes Completed.
12. Timeline records every transition.

Also test:

1. Team submits fix.
2. Reviewer requests changes.
3. Reason is saved.
4. Team receives the reason.
5. Issue returns to investigation.
6. Team can submit another fix.
7. Reviewer can review again.

Do not use fake state changes or hardcoded data.

Make the entire workflow persistent in PostgreSQL and reflected immediately across the dashboard, issue detail page, action center, notifications, and timeline.

The final experience should communicate:

TEAM:
"We fixed it."

MERCHANT VOICE:
"Great. Prove it."

REVIEWER:
"I verified it."

SYSTEM:
"Now it is completed."

This verification loop is a core product feature and should feel seamless, trustworthy, and production-ready.
```
